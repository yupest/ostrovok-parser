## Структура репозитория

```
.
├── ostrovok_hotels.py        # Шаг 1: парсинг списка отелей + каталог
├── ostrovok_rooms.py         # Шаг 2: парсинг номеров и цен
├── ostrovok_statistic.py     # Шаг 3: сводная статистика за день
├── capacity_utils.py         # Оценка вместимости номера
├── log_config.py             # Логирование + Telegram-уведомления
├── daily/
│   ├── hotels/               # YYYY-MM-DD.csv — отели за день
│   ├── rooms/                # YYYY-MM-DD.csv — номера за день
│   └── statistics/           # YYYY-MM-DD.csv — статистика за день
├── catalog/
│   └── hotels.csv            # Накопительный каталог отелей
├── logs/                     # Логи запусков
└── .github/workflows/
    └── ostrovok-parser.yml   # Ежедневный запуск в GitHub Actions
```

## Форматы данных

### `daily/hotels/YYYY-MM-DD.csv`

| Колонка | Описание |
|---|---|
| `city` | Город |
| `ota_hotel_id` | Идентификатор отеля в Ostrovok |
| `master_id` | Master ID отеля |
| `name` / `name_en` | Название (рус./англ.) |
| `address` | Адрес |
| `latitude` / `longitude` | Координаты |
| `url` | Ссылка на страницу отеля |
| `rooms_number` | Общее число номеров в отеле |

### `daily/rooms/YYYY-MM-DD.csv`

| Колонка | Описание |
|---|---|
| `ota_hotel_id`, `master_id` | Идентификаторы отеля |
| `room_name` | Название номера |
| `rg_hash` | Хеш группы номеров (ключ группировки) |
| `count_rg_hash` | Сколько тарифов объединено в группу |
| `allotment` | Кол-во свободных номеров этого типа |
| `bedding_type`, `beds`, `bedding_data`, `multi_bed_data` | Информация о кроватях |
| `capacity` | Оценённая вместимость одного номера (гостей) |
| `price_rub_min` / `price_rub_max` | Мин./макс. цена за ночь, ₽ |
| `url` | Ссылка на страницу отеля |

Если по отелю API не вернул тарифов, в файл пишется строка-заглушка с пустым `rg_hash` — для контроля пропусков.

### `daily/statistics/YYYY-MM-DD.csv`

| Колонка | Описание |
|---|---|
| `ota_hotel_id`, `name` | Отель |
| `date` | Дата сбора |
| `rooms_num` | Всего номеров в отеле |
| `free_rooms_amount` | Сумма allotment по всем типам номеров |
| `max_capacity` | Суммарная вместимость свободных номеров |
| `available_rooms_percent` | Доля свободных номеров, % |
| `min_price` | Минимальная цена за ночь, ₽ |

### `catalog/hotels.csv`

Те же поля, что и в дневном файле отелей, плюс `first_seen_date` и `last_seen_date` — когда отель впервые и в последний раз встречался в выдаче.



## Полнота поиска и ошибки пагинации

Поиск выполняется с `type_tab=hotels`, без `type_group`. Включает гостиницы, хостелы,
гостевые дома, апарт-отели, коттеджи, кемпинги и другие категории вкладки hotels.
Отдельные квартиры (APARTMENT) исключаются. Тип `kind` сохраняется из API в
дневной список, каталог и статистику. При проверке карточек тип уточняется из
структурированных данных карточки. Известные квартиры помечаются в каталоге
`monitoring_scope=excluded_apartment`, сохраняются как справочные записи, но не
добавляются в ежедневный расчёт как 100% загрузки.
Даты проживания: заезд завтра, выезд послезавтра, один взрослый.

Парсер накапливает порции API до `search_finished=true`, затем сверяет число уникальных
объектов с `total_av_hotels`. Пустой промежуточный ответ не является концом списка.
Счётчик и порядок живой выдачи могут меняться во время обхода. Если после короткой
последней страницы за расчётной границей выдачи получено три подряд завершённых
пустых ответа без ошибок, допускается небольшой недобор: до 1% счётчика, минимум
2 и максимум 20 объектов. Сохраняются только реально найденные записи, а расхождение
фиксируется предупреждением и `outcome=completed_with_count_drift` в JSON-диагностике.
Это не подтверждение, что недостающие объекты были собраны. Большой недобор,
повтор непустой страницы и сетевые ошибки таким условием не маскируются.
HTTP-ошибки, некорректный JSON, незавершённый поиск, повтор страницы без новых объектов
и достижение лимита страниц приводят к повтору, а затем к ошибке запуска. Неполный
сбор отелей не сохраняется, следующие этапы workflow не выполняются.
Диагностика каждой попытки: `logs/YYYY-MM-DD-search.json`. При успешном запуске
логи коммитятся вместе с данными; при ошибке сообщения доступны в журнале Actions. Ключи сессий и cookies в диагностику не записываются.
Это проверка полноты относительно числа, сообщённого API, а не гарантия наличия
всех работающих средств размещения региона. Поиск по-прежнему зависит от дат и гостей.

Настройки: `SEARCH_PAGE_TIMEOUT_MS=90000`, `SEARCH_PAGE_RETRIES=3`,
`SEARCH_MAX_PAGES=500`. Достижение лимита не считается успешным концом выдачи.

## GitHub Actions

Workflow `Ostrovok Parser` запускается ежедневно в 08:00 UTC (16:00 по Иркутску)
и вручную через Run workflow. Тесты выполняются перед сбором, параллельные сборы
сериализованы. Лимит задания — 180 минут.

Пользовательские Secrets не требуются. Checkout использует автоматически созданный
GitHub токен; `permissions: contents: write` позволяет сохранять CSV в этом репозитории.
Telegram и отправка в MALISMF/parsers отключены. Данные сохраняются в daily/ и catalog/.
Право локального PAT менять файл workflow — отдельное от токена самого задания Actions.

## Отсутствие предложений и контрольные даты

Если известного объекта нет в дневной выдаче, сначала проверяется его карточка.
Квартиры исключаются; неактуальные карточки помечаются inactive и больше не
запрашиваются, если объект сам не появится в поиске. Сетевая ошибка не деактивирует карточку.

Для актуального объекта проверяются ночи пн–вт через 1, 2 и 3 календарных месяца
от исходной даты заезда. Берётся первый понедельник не раньше соответствующей
даты месяца (день месяца ограничивается последним днём месяца).

- Есть предложения хотя бы на одну контрольную ночь — collection_status=
  assumed_full_future_available, 0 свободных / 100% загрузки на исходную ночь.
- Все три контрольных ответа пусты — no_future_offers, показатели за исходный
  день остаются неизвестными и не участвуют в средней загрузке.
- Нет положительного ответа и есть ошибка — future_check_error, показатели также
  неизвестны, проверка повторяется при следующем ежедневном запуске.

Контрольные ответы принимаются только для правильного master_id. Пустые rates=null
при HTTP 200 и подтверждённом идентификаторе означают отсутствие предложений.
Фактическая доступность на контрольные даты не прибавляется к исходной дате.
Положительный результат прекращает дальнейшие запросы. Если объект найден в
поиске, но прямой запрос номеров пуст, применяется та же проверка контрольных дат.
Старое правило «актуальная карточка сама по себе = 100%» больше не применяется.

Каталог, дневной список и статистика сохраняют future_availability_status,
availability_checked_date, control_dates и control_results (JSON с датами,
HTTP-статусами и количеством предложений). Поля card_status, card_checked_date и
card_check_reason отвечают только за существование карточки. Неудачный запрос
номеров никогда не считается подтверждённой полной загрузкой.

Это согласованная эвристика, а не подтверждённая площадкой фактическая занятость.
